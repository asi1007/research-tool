# /market-research

Keepa Product Finder で「安い・売れてる・出たばかり」の商品を探し、未知の ASIN だけを自動調査タブへ積む。続けて `fetch_products.py` を呼び、商品情報まで埋める。

## 実行（この順に最後まで通す）

**探索して終わりにしない。仕入先調査まで進めて初めて1回分。**
1〜3 は CLI、4 はブラウザ操作。件数が多いので **4 に入る前に必ず件数をユーザーへ伝える**。

```bash
# 1. 前回ユーザーが A列に印を付けた行を移す（d=候補外、s=季節商品、p=保留。いずれも次回から候補に出ない）
.venv/bin/python drop_marked.py --dry-run       # まず対象を見る
.venv/bin/python drop_marked.py

# 2〜3. 探索 → 商品情報 → 利益・ROIの数式 → 短縮名 → 検索ワード/広告単価 → 季節商品の振り分け まで一続きに走る
.venv/bin/python discover_products.py --all-sheets
```

```
# 4. 仕入先調査（1688の画像検索）。/find-supplier の手順に従う
#    ブラウザ（claude-in-chrome）必須。1件あたり5〜8手、キャプチャで止まったら中断して報告する
```

- `--sheet` … 対象タブを1つに絞る。省略時は価格帯を読み取れる自動調査タブすべて
- `--no-fetch` … 自動調査タブへ ASIN を書くところで止める（商品情報も短縮名も取らない）
- `--no-shorten` … H列の短縮名を書かない
- `--no-keywords` … M列の検索ワードとY列の広告単価を書かない
- `--no-seasonal` … 夏物・冬物を「季節商品」タブへ移さない
- `--limit` … タブごとの追記件数の上限
- `--max-pages` … Product Finder を引くページ数の上限（既定 20）。トークンが少ないときに絞る
- `--max-lookups` … 月商を実測する件数の上限。**1件1トークン**なので枯渇を避けたいときに使う
- `--max-age-days N` … 出品からの経過日数の上限（既定 365）。下記「出品からの期間を変える」
- `--no-age-limit` … 出品からの経過を問わない。`--max-age-days` とは同時に使えない
- `--debug` … DEBUG ログを出す

`--dry-run` は発見件数と ASIN 一覧を表示するだけで、シートには一切書き込まない。
**dry-run では実測（`/product`）を行わない。** 1件1トークン消費するため、書き込まない確認では問い合わせない。

### トークンが足りないと待機で数時間かかる

Product Finder は **1ページ11トークン**、実測は **1件1トークン**。補充は **5トークン/分**。
`max_age_days` を 365 に広げた 2026-08-31 は、残10トークンからの実行で探索だけで200トークン超が必要になり、
`--dry-run` すら7分でタイムアウトした。**条件を広げるときは `https://api.keepa.com/token` で残量を確認してから回す。**

**実測はクエリより重い。** 2026-09-03 に365日条件で **636件（13ページ）** の候補が取れたが、
その後の実測（1件1トークン）でトークンが尽き20回リトライして落ちた。補充は 5/分なので
500件なら100分かかる。**定期実行は `--max-lookups 150` を付けて確実に完走させ、残りは翌日に回す。**

**トークンが足りないと残高がマイナスになり、1ページ目すら取れない。** Keepa は不足していても
リクエストを受け付け、`tokensLeft` を負の値にする。ログの `tokens_left: -7` がこれで、
リトライのたびに再びマイナスへ落ちるため19回待っても page 0 が返らなかった（2026-08-31）。
**日中に条件を広げて手動実行しない。夜間にトークンが貯まる定期実行（毎日 06:30）に任せる。**
急ぐときは `--max-pages 1` で上位50件だけ引く。

## 出品からの期間を変える

「期間を伸ばして」「期間を外して」「2年以内で」と言われたら、**コードの既定値ではなく CLI オプションで渡す。**

```bash
.venv/bin/python discover_products.py --sheet 自動調査500円以下 --max-age-days 1095   # 3年以内
.venv/bin/python discover_products.py --sheet 自動調査500円以下 --no-age-limit         # 期間を問わない
```

- **「今回だけ」ならオプションで渡すだけ。** 定期実行（`--all-sheets`、既定 365日）には影響しない
- **恒久的に変えると言われたときだけ** `DEFAULT_MAX_AGE_DAYS`（`discovery_criteria.py`）を変える。
  全タブに効くので、トークン消費が増える点を先に伝える
- **対象タブを `--sheet` で絞る。** `--all-sheets` と組み合わせると全価格帯で候補と実測が増え、トークンが尽きる
- 年数・月数で言われたら日数に直す（1年=365、2年=730、3年=1095）

**期間を外すと国内ブランド品が大量に混ざる。** 2026-09-17 に500円以下を期間なしで引いたところ、
月1,000個以上の候補は 2件 → **49件**に増えたが、36ヶ月超と出品日不明の29件は大半が
トンボ・ゼブラ・パイロット・コクヨ・IKEA だった。月商50万円以上の7件のうち扱えるのは4件で、
うち3件は出品から12〜24ヶ月。**期間の条件はブランド品よけとしても効いている。**
期間を外したあとは、報告時に扱えない商品（ブランド品・印鑑など）を指摘して A列に `d` を付けてもらう。

## 同じシートへの書き込みを重ねて走らせない

`fetch_products` は取得に時間がかかる。その間に行が挿入・削除されると、読み取り時の
行番号は別の商品を指す。**書き込む直前に ASIN で引き直すよう直した**（`row_relocator.py`）が、
そもそも重ねて起動しないこと。

2026-09-05 に、Keepa のトークン待ちで進んでいないと誤認して `fetch_products` を
何度もバックグラウンド起動し、同時に `rival_research.py write` で行を挿入した結果、
**8行が1行ずれて書き込まれた**。自社行の商品名が競合の商品名で上書きされていた。

- **`| tail -N` を付けてバックグラウンド実行すると、完了まで何も出力されない。**
  出力が空なのを「動いていない」と誤読して再起動した。進捗を見たいならパイプを外す
- **進まないときはまず Keepa のトークン残量を見る。** `https://api.keepa.com/token?key=...`。
  マイナスなら待つしかない（補充 5/分）。起動を重ねても速くならない
- 状態の確認は `--count-only`（書き込まない）

## 定期実行

`com.wada.market-research` が毎日 06:30 に `discover_products.py --all-sheets` を実行する。
**CLI の 2〜3 だけが自動で回る。** 1（d行の退避）と 4（仕入先調査）は人の判断・ブラウザが要るため入っていない。

## 利益・ROI などの数式は既存行から写す

`fill_formulas.py` が ROI・投資額・月間販売高・リターン・利益率・利益・関税・原価の**空欄**へ、
同じタブの既存行の数式を雛形にして行番号だけずらして入れる。`discover_products.py` の中で商品情報の取得の直後に走る。

- **2026-09-17 まで定期実行に入っておらず、自動で積んだ行はすべて数式が空だった**（580セル）。
  以前は月間販売高・利益・利益率の3列だけを対象にしていた
- **購入価格（PRICE_LOWEST 等）は対象外。** 仕入先を書くときに数量倍率つき（`=U16*24*10`）で入るため、雛形で埋めると倍率が消える
- **自分の行を参照していない数式は雛形にしない。** 別のタブから写した行は元の行番号を指したままのことがある
- 仕入先が未入力の行は `#N/A` になる（購入価格が空だと数式が `NA()` を返す）。正常

## 短縮名（H列）には入数を `×30` で入れる

`shorten_titles.py` が `claude -p` に投げるプロンプトで指示している。**上限は13文字**
（商品名10文字＋数量3文字を想定。2026-09-05 に10文字から広げた）。

| 元の商品名 | 短縮名 |
|---|---|
| アンブレラマーカー 30個セット シリコンリング | `傘マーカー×30` |
| 靴下 メンズ ソックス 5足セット | `靴下×5` |
| メジャー 巻き尺 150cm 2WAY | `メジャー`（単品は付けない） |

- **`×1` は付けない。** 入数が書かれていない単品はそのまま
- 上限を超えた短縮名は**その項目だけ落として次回に回す**。バッチ全体は捨てない

## 検索ワードと広告単価は Amazon Ads API から取る

`fill_keywords.py` が ASIN ごとに **推奨キーワード**（`/sp/targets/keywords/recommendations`）を引き、
上位3件を **M列『検索ワード』** に、対応する完全一致の推奨入札額を **Y列『広告単価』** に改行区切りで書く。

- **`bid` は円の1/100で返る。** `9700` は 97円。そのまま書くと100倍になる
- 資格情報は広告プロジェクトと共有する（`.env` の `AD_CREDENTIALS_ENV` が
  `data-engineer/dwld-ad-data/.env` を指す）。同じものを二重に持たない
- **手入力の値は上書きしない。** M列・Y列のどちらかが埋まっている行は飛ばす
- **N列『検索数』は Ads API では取れない。** Amazon の公式APIに検索ボリューム（絶対値）は無い。
  この列はセラースプライトからの手入力のまま

## 検索順位（BT列）は Brand Analytics から取る

`fill_search_rank.py` が **検索キーワードレポート**（`GET_BRAND_ANALYTICS_SEARCH_TERMS_REPORT`）を引き、
M列の検索ワードごとの **`searchFrequencyRank`** を BT列『検索順位』へ改行区切りで書く。**小さいほどよく検索されている**。

```bash
.venv/bin/python fill_search_rank.py --dry-run     # 対象行だけ見る
.venv/bin/python fill_search_rank.py               # 全自動調査タブへ書く
.venv/bin/python fill_search_rank.py --refresh     # キャッシュを捨ててレポートを取り直す
```

- **`dataStartTime` は日曜でないと FATAL になる**（`dataStartTime must be a Sunday when reportPeriod=WEEK`）
- レポートは **43万〜130万語・数十MB**。週次更新なので `data/search_rank_YYYY-MM-DD.json` にキャッシュし、同じ週は取り直さない
- **検索数ではなく順位。** セラースプライトの「検索数」とは別の指標なので、N列とは分けてある
- 生成に1〜2分かかる。`GET_BRAND_ANALYTICS_SEARCH_QUERY_PERFORMANCE_REPORT` は `asin` 必須で自社商品専用のため使えない

## 有名ブランドは Keepa のブランド欄で弾く

実測後に `select_by_revenue` が除外する。Keepa のクエリではブランドを絞れないため。
**「有名ブランドを外して」「このブランドも外して」と言われたら、下の一覧に足す。**

| 一覧（`discovery_criteria.py`） | 照合先 | 入れるもの |
|---|---|---|
| `EXCLUDED_MAKERS` | **ブランド欄・メーカー欄だけ** | 有名ブランド全般（トンボ・ゼブラ・パイロット・ぺんてる・三菱鉛筆・コクヨ・パナソニック・ZIPPO・エンスカイ・IKEA・テルモ・ミカサ・サーモス・3M・ニチバン） |
| `EXCLUDED_BRANDS` | ブランド欄・メーカー欄。**両方空なら商品名** | 商品名で探しても誤爆しない名前（タカラトミー・山崎実業・無印良品など）。`/rival-research` も商品名で使う |

- **有名ブランドを商品名で探してはいけない。** 「サーモス 交換用部品」（ブランドは FUYUERO の互換品）や
  「ゼブラ柄」まで弾いてしまう。季節商品の誤移動と同じ失敗で、商品名には用途・対応機器の説明が混ざる
- ブランド欄は `トンボ(Tombow)` `IKEA (イケア)` のように併記される。括弧で区切った各部分と完全一致で照合する
- **ブランド欄が取り違えられていることがある。** `Zebra Technologies`（別会社）のゼブラ替芯はメーカー欄
  `ゼブラ(ZEBRA)` で弾いている。両方を見るのはこのため
- 2026-09-17 にユーザーが d を付けた25件のブランドが起点。170件の実データで54件が弾かれた
- **既にタブに積んだ行は消えない。** 足したあとは既存行に d を付けてもらうか、確認して `drop_marked.py` で移す
- 1688 に同款が無い（タカラトミー・オムロン・コールマン）、日本の生活雑貨メーカー（レック・ダルトン・
  山崎実業・無印良品・アイリスオーヤマ・ニトリ など）は `EXCLUDED_BRANDS`。
  **`EXCLUDED_BRANDS` には誤爆しやすい短い綴りを入れない**（`lec` は select / electric に含まれる）

## カテゴリは SP-API の表示グループから取る

`salesRanks[].displayGroupRanks[].title`（例「DIY・工具・ガーデン」）を使う。**日本語のまま入れる。**
無ければ `classificationRanks[].title`（例「浴室水栓用パーツ」）で代用し、順位が最も上のものを選ぶ。

## シートを大きく触るときはクォータに注意

Sheets API は **読み書きとも 60req/分**。列の一括操作で何度も踏んだ（2026-09-03）。

- **1タブ1リクエストにまとめる。** `deleteDimension` を1列ずつ送ると 204回で即超過する
- **`worksheet()` は毎回メタデータを読む。** 検証のための `read_values` を挟むと読み取り側が先に尽きる。
  全タブの状態を見るなら `read_all_values`（`values_batch_get` で1回）を使う
- 429 が出ても**途中まで適用されている**。列コードで対象を探す作り（冪等）にしておき、90秒待って再実行する

## 夏物・冬物は「季節商品」タブへ自動で移す

`move_seasonal.py` が季節商品と判定した行を **季節商品タブへ移して元タブから削除する**。
`discover_products.py` の最後に走るので、通常は個別に叩かなくてよい。

```bash
.venv/bin/python move_seasonal.py --dry-run                      # 対象を見る（判定は保存しない）
.venv/bin/python move_seasonal.py                                # 全自動調査タブから移す
.venv/bin/python move_seasonal.py --not-seasonal B0XXXXXXXX ...  # 人が「季節商品ではない」と判断したものを記録
```

**判定は2段階。キーワードは候補を絞るだけで、移すかは Claude が決める。**

1. 商品名に季節のキーワード（`src/usecases/seasonal.py`）があれば候補にする
2. 候補を `claude -p` に渡し、「夏か冬にしか需要が無い商品か」を判定させる
3. 判定は `data/seasonal_verdicts.json` に ASIN ごとに残し、**同じ ASIN は二度と聞かない**

- **「これは季節商品じゃない」と言われたら、行を戻したうえで `--not-seasonal` で記録する。**
  人の判断は Claude の判定より優先され、翌朝の定期実行でも移されない。記録しないと、判定ファイルを
  消したときに再判定で移される可能性が残る
- **判定に失敗した候補は移さず exit 1。** 誤って移すと元タブから消えて誰も気づけないため。次回また判定する
- `data/` は gitignore されている。判定ファイルはこのマシンにしか無い
- **プールバッグ・夏用キャップ・水着インナー・水泳帽も季節商品**（2026-09-03 にユーザー判断）。プロンプトの例に入れてある

**なぜ2段階か（2026-09-17）。** 以前はキーワードに当たっただけで移していた。商品名には用途・対応機器の説明が
混ざるため、11件を誤って移し、うち7件は5日間だれも気づかなかった。

| 商品 | 反応した語 | 商品名の中での意味 |
|---|---|---|
| 布団用の洗濯ネット 5件 | `毛布` | 毛布も洗える |
| ホコリ取りスポンジ 2件 | `ファン` | ファンブレードの掃除用 |
| デジタル温湿度計 | `熱中症` | 熱中症の目安を表示 |
| PH試験紙 | `プール` | プールの水質検査にも使える |
| Micro USBケーブル | `加湿器` | 加湿器等に対応 |
| 本のカバーフィルム | `uvカット` | 本の日焼け防止 |

Claude に判定させたところ、この11件はすべて「季節商品ではない」、季節商品タブの本物は大半が「季節商品」になった。

**行を別のタブへ移すときは `plan_transfer`（`src/usecases/drop_marked.py`）を使う。** 数式の行番号と列を
移動先に合わせて付け替える（移動先に無い列を指す数式は書かない）。季節商品・候補外への移動はどちらもこれを通る。

2026-09-17 までは数式を文字列のまま写していたため、移した先で**元のタブの行番号を参照したまま**になり、
別の商品の値で利益を計算していた。季節商品タブでは54行が該当し、昔の列配置のまま
「購入価格 = 販売手数料 × 24」を計算している行もあった。自動調査タブの数式を見本に直した
（購入価格の末尾の係数 `*24*7` などは手入力の可能性があるので残した）。**候補外タブは直していない。**

## A列の印で行を移す（`d`=候補外、`s`=季節商品、`p`=保留）

ユーザーは自動調査タブの **A列に印** を付けて判断を残す。`drop_marked.py` が印ごとに
**移動先のタブへ移してから元タブの行を削除する**。

| 印 | 意味 | 移動先 |
|---|---|---|
| `d` | 不要 | 候補外 |
| `s` | 季節物（2026-09-17 に追加） | 季節商品 |
| `p` | 判断保留（2026-09-17 に追加） | 保留 |

- **「印を付けた行を移して」「d削除」「d対応」「sは季節物へ」「pは保留へ」と言われたら `drop_marked.py` を実行する。** 手で行を写さない
- 全角（`ｄ` `ｓ`）・大文字も同じ扱い。移動先の一覧は `MARK_DESTINATIONS`（`src/usecases/drop_marked.py`）。
  **新しい印を増やすときはここに1行足すだけ**
- 候補外・季節商品・保留はいずれも既知ASINの突合対象なので、移した ASIN は二度と自動調査タブに積まれない
- 数式は移動先の行・列に付け替えて写す（`plan_transfer`）
- **印ごとに読み直してから移す。** 先に `d` の行を消すと、`s` の行番号がずれるため

**消すだけにしてはいけない。** 行を消しただけでは既知ASINから外れ、翌朝の定期実行でまた積まれる。

**`s` を付けた商品は、Claude の季節判定を通らずに季節商品へ入る。** 人の判断なので、
判定ファイル（`data/seasonal_verdicts.json`）に記録する必要はない（元タブから消えるので再判定もされない）。

## 価格帯はタブ名から読む（コードに書かない）

**タブを増やすだけで新しい価格帯を回せる。** `DiscoveryBand.from_sheet_name()` がタブ名を解釈する。

| タブ名 | 価格帯 |
|---|---|
| `自動調査1000円以下` | 1〜1000円 |
| `自動調査1000円-2000円` | **1001**〜2000円 |
| `自動調査3000円以上` | 3001円〜（上限なし） |

- **境界は重ならない。** `A円-B円` の下限は `A+1` 円。`1000円以下` と `1000円-2000円` で 1000円ちょうどの商品が二重に積まれない
- 全角数字・全角ハイフン（`自動調査１０００円ー２０００円`）も NFKC 正規化して読む
- **読み取れないタブ名を渡すと実行せず exit 1。** 価格帯不明のまま既定の条件で書き込む事故を防ぐため
- `--all-sheets` は**前のタブで積んだ ASIN を次のタブへ積まない**（同一実行内でも突合する）

**タブを新設したら見た目を揃える。** 手で作ったタブは列幅が全列 100px・固定行なし・表示形式なしで、
価格が `7.2` のまま並び関税や利益の桁が読めない。`align_appearance.py` が既存タブから
列幅・非表示列・固定行/列・行の高さ・表示形式を写す。

```bash
.venv/bin/python align_appearance.py <タブ名>            # --dry-run で送るリクエストを確認
.venv/bin/python align_appearance.py <タブ名> --reference 自動調査2000円以上
```

**背景色とリンクは写さない。** 背景色は `cell_highlighter` が「自動で埋めたセル」の印に使っており、
`textFormat.link` は仕入先URLのリンクなので、上書きすると情報が消える。
見本の書式は先頭 10 データ行の**最頻の書式**から採る（見本側にも書式の抜けた行が混ざるため）。

`--dry-run` は発見件数と ASIN 一覧を表示するだけで、シートには一切書き込まない。
**dry-run では実測（`/product`）を行わない。** 1件1トークン消費するため、書き込まない確認では問い合わせない。

### トークンが足りないと待機で数時間かかる

Product Finder は **1ページ11トークン**、実測は **1件1トークン**。補充は **5トークン/分**。
`max_age_days` を 365 に広げた 2026-08-31 は、残10トークンからの実行で探索だけで200トークン超が必要になり、
`--dry-run` すら7分でタイムアウトした。**条件を広げるときは `https://api.keepa.com/token` で残量を確認してから回す。**

**実測はクエリより重い。** 2026-09-03 に365日条件で **636件（13ページ）** の候補が取れたが、
その後の実測（1件1トークン）でトークンが尽き20回リトライして落ちた。補充は 5/分なので
500件なら100分かかる。**定期実行は `--max-lookups 150` を付けて確実に完走させ、残りは翌日に回す。**

**トークンが足りないと残高がマイナスになり、1ページ目すら取れない。** Keepa は不足していても
リクエストを受け付け、`tokensLeft` を負の値にする。ログの `tokens_left: -7` がこれで、
リトライのたびに再びマイナスへ落ちるため19回待っても page 0 が返らなかった（2026-08-31）。
**日中に条件を広げて手動実行しない。夜間にトークンが貯まる定期実行（毎日 06:30）に任せる。**
急ぐときは `--max-pages 1` で上位50件だけ引く。件数感を先に見てから `--limit` を決めること。

## 抽出条件（`DiscoveryCriteria`）

閾値を変えるときは `src/domain/value_objects/discovery_criteria.py` の `DiscoveryCriteria` を触る。ここ1箇所に集約してある。

| 条件 | 値 |
|---|---|
| 価格（`current_NEW`） | タブ名から決まる（上表） |
| 月商（販売数 × 価格） | **50万円以上**（Keepa は積で絞れないため、帯の上限価格で足切りしてから実測で絞る） |
| 出品からの経過（`listedSince_gte`） | **365日以内**（2026-08-31 に180日から変更。1回だけ変えるなら `--max-age-days` / `--no-age-limit`） |
| 商品タイプ（`productType`） | `[0]`（標準品のみ） |
| Amazon本体の出品（`availabilityAmazon`） | `[-1]`（本体が売っていないもの） |
| 除外カテゴリ（`categories_exclude`） | 21カテゴリ（本・DVD・食品・ベビー用品・**ビューティー**・**トレカ**など中国輸入で扱えないもの） |
| 並び順 | `monthlySold` 降順 |
| `perPage` | 50 |

**実測値（2026-08-29）**: 条件のみで202件 → Amazon本体の出品を除外して88件 → 除外カテゴリを引いて62件。CLI の実機実行ログは `found: 59, new: 55`（`found` は条件に合う件数、`new` はそこから全タブの既知ASINを除いた未知件数）、`--limit 3` で3件を書き込み確認済み。

## Keepa の落とし穴（知らないと必ず詰まる）

1. **`releaseDate` は使えない。** 発売日が入っている商品はごく一部で、大半は 0 が返る。「出たばかり」の判定は `listedSince`（Amazon への出品日）を使う
2. **Amazon本体の除外は `availabilityAmazon: [-1]`。** `current_AMAZON` を範囲指定（例: `current_AMAZON_gte/lte`）で除外しようとすると **0件になる**。`-1`（出品なし）は範囲比較の対象外の値のため
3. **`categories_exclude` は categoryTree を見るので、ツリーが空の商品は弾けない。** 2026-09-03 に
   食品（`B0GPQB656T` 中華春雨、rootCategory=57239051）が1件すり抜けた。除外カテゴリなのにクエリで
   落ちなかったのは `categoryTree` が空だったため。**実測した `rootCategory` でもう一度ふるいにかける**
   （`select_by_revenue`）
4. **ポケモンカードはルートでは落とせない。** トレカは「ホビー」配下（`2189358051` コレクションカード・アクセサリ、`10345415051` トレーディングカードゲーム）にあり、ホビーごと除外するとプラモ・鉄道模型まで落ちる。**サブカテゴリ指定で除外する**
5. **化粧品はルートカテゴリ「ビューティー」(`52374051`) ごと除外している。** 薬機法で化粧品は輸入できないため。サブカテゴリ（スキンケア・メイクアップ等）単位ではなくルートで落としているので、メイクブラシ・パフのような雑貨も巻き添えで落ちる
6. **`perPage` は50未満だと400エラー**（`combination of perPage and page exeeds limit or is too small`）。1回のクエリで11トークン消費する

## 突合の仕様

- 既知 ASIN の判定は、ASIN 列（`ASIN_SELL`）を持つ**全タブ**を `values_batch_get` で1回に読んで突合する。タブごとに読むと Sheets の読み取りクォータ（429）に当たる（開発中に実際に踏んだ）
- **「候補外」タブも突合対象に含めている。** 一度落とした商品を再び「自動調査」タブへ積まないため
- 書き込み先は C列（`ASIN_SELL`）に ASIN、L列（`NOTE_BUY_OTHER2`）に `自動調査YYYY-MM-DD`

## 結果の報告

見つかった ASIN は `https://www.amazon.co.jp/dp/<ASIN>` のリンクで報告する（親リポジトリの規約）。

## 0件は正常

ログの `found`（条件に合う件数）と `new`（そこから既知ASINを除いた未知件数）は意味が違う。**`new: 0` は毎日ありうる正常な結果で、条件を緩める理由にはならない。** 前日までに大半が「自動調査」タブや他タブへ積まれていれば、条件は変わらなくても新規に見つかる件数は自然に減っていく。

条件が厳しすぎると疑ってよいのは `found` 自体が0（またはごく少数）のときだけ。その場合は次の順で緩める。

1. 月商（`min_monthly_revenue_yen`）を下げる
2. 価格帯を広げる（タブを増やす。`max_price_yen` はタブ名から決まる）
3. 経過日数（`max_age_days`）を伸ばす
